# 決策紀錄

記錄 Brevora 從「自己用的工具」整理成「可公開展示的作品」時做的關鍵決策：當時的限制、考慮過的選項、依據的證據，以及接受的取捨。

程式碼由 AI（Claude Code）撰寫；以下的問題定義、選項取捨與優先順序由我決定。

---

## 1. 作品集用「前端 Demo 模式」部署，不採用 Supabase

**限制**

- 面試官會從履歷上的連結自己點開，時間可能是投遞後幾天，也可能是幾週後
- 必須免登入就能體驗核心價值：訂閱影片 → AI 節目筆記
- 只用免費方案

**考慮過的選項**

| 選項 | 問題 |
|------|------|
| 完整部署（FastAPI + PostgreSQL + Google 登入） | 讀取訂閱需要 `youtube.readonly` 權限，App 通過 Google 驗證前只有 Test users 名單內的帳號能登入（見 [google_setup.md](google_setup.md)），面試官根本無法進入；就算通過驗證，要求授權 YouTube 帳號對只想花一分鐘看作品的人門檻也太高 |
| Supabase 免費方案當資料庫 | 免費專案一週沒有資料庫活動就會被暫停（[官方文件](https://supabase.com/docs/guides/platform/free-project-pausing)）。履歷連結的點擊頻率遠低於一週一次，面試官點開時很可能剛好遇上暫停 |
| **前端 Demo 模式 + 預先生成的真實資料（採用）** | 無法即時為新影片生成筆記 |

**決策**

- 前端設定 `VITE_DEMO_MODE=true` 時，API 呼叫改由瀏覽器內的 demo 層回應（`frontend/src/lib/demo.ts`），畫面與正式版是同一套元件
- 筆記用 `scripts/generate_demo_data.py` 產生：它呼叫的是產品本身的 `app.services.ai`，所以 demo 呈現的就是產品的實際輸出，不是手寫範例
- 收藏、已讀、釘選頻道存在訪客自己的瀏覽器（localStorage），可以實際操作
- Vercel 靜態部署，沒有伺服器會休眠或暫停
- 正式版 build 不會打包 demo 資料（demo 程式以動態載入切成獨立檔案，只有 demo build 才會產生）

**取捨**

- Demo 只有 6 支影片，「同步」與「生成筆記」不會真的執行，畫面會說明原因
- 完整版仍保留在 repo，可依 README 在本機執行

## 2. YouTube 封鎖雲端主機 → 改由 Gemini 直接讀影片網址

**問題**

原本取得影片內容有兩條路：用 `youtube-transcript-api` 抓字幕，抓不到時用 `yt-dlp` 下載音訊再交給 AI。兩條路都要伺服器直接連 youtube.com，而 YouTube 會對雲端主機的 IP 回傳機器人驗證頁。

**證據**

2026-09-24 在雲端容器中重現：

```bash
curl -sL -A "Mozilla/5.0 ..." "https://www.youtube.com/watch?v=8BtHk-oNlN0"
```

- HTTP 狀態碼是 200，但頁面內容是驗證頁，不是影片
- 頁面中的 `playabilityStatus` 為 `LOGIN_REQUIRED`
- 頁面文字：「Sign in to confirm you're not a bot」

所以這不是「偶爾失敗」：只要部署到雲端，字幕與音訊兩條路都拿不到內容。在本機開發時不容易察覺這個問題。

**決策**

- 把 YouTube 網址直接交給 Gemini（`file_data`），由 Google 端讀取影片，伺服器不再接觸 youtube.com
- 移除 `yt-dlp`、`youtube-transcript-api`、`ffmpeg`，部署需求變少
- 影片標題、頻道、長度等資料改用官方的 YouTube Data API v3（用 API key 驗證，不受機器人驗證影響）

**實測**

2026-09-24 生成 demo 資料（`gemini-3.6-flash`、低媒體解析度）：

| 影片 | 長度 | 生成時間 |
|------|------|----------|
| How I AI — Opus 5.5 與 GPT-6 Sol 實測 | 38 分 | 46 秒 |
| How I AI — 7 個 Grok Bot 代理 | 36 分 | 82 秒 |
| The Diary Of A CEO — Andrew Huberman | 136 分 | 127 秒 |
| The Diary Of A CEO — 億萬富豪警告 | 105 分 | 122 秒 |
| Starter Story — Roblox 百萬富翁 | 20 分 | 39 秒 |
| Starter Story — 複製 3 款 App | 13 分 | 37 秒 |

兩小時以上的影片也能在約兩分鐘內完成。另外用 REST API 測過一支 13.6 分鐘的影片，約消耗 7.4 萬 tokens。

**取捨**

- 只支援公開影片
- 依賴 Gemini 對 YouTube 網址的支援
- Gemini 免費方案每天最多處理 8 小時的 YouTube 影片（[官方文件](https://ai.google.dev/gemini-api/docs/video-understanding)），所以 demo 資料生成腳本會跳過已完成的影片，額度用完隔天可以接著跑

## 3. Gemini 舊模型退役 → 模型名稱改為可設定

**問題**

程式寫死 `gemini-2.5-flash`，備援是 `gemini-2.5-flash-lite`。Google 對新申請的 API key 回應這兩個模型「no longer available to new users」，所以任何人照 README 重新設定，AI 筆記都會失敗。原本使用的 `google-generativeai` SDK 也已停止支援。

**決策**

- 改用 `google-genai` SDK
- 模型名稱改由環境變數設定：`GEMINI_MODEL`（預設 `gemini-3.6-flash`）、`GEMINI_FALLBACK_MODEL`（預設 `gemini-3.5-flash`）。下次模型退役時，改設定就好，不必改程式
- 主要模型失敗時自動改用備援模型

**驗證（2026-09-24）**

- 把 `GEMINI_MODEL` 設成不存在的名稱 → 主要模型回 404 → 自動改用備援模型並成功回傳
- 端到端測試時遇到主要與備援模型在同一分鐘都回傳 503（Google 端高負載）。SDK 預設不重試，所以對暫時性錯誤（408 / 5xx）補上指數退避重試，重試仍失敗才換備援模型
- 生成 demo 資料時遇到兩種額度限制，兩個模型各自卡在不同的地方：

  | 模型 | 回傳的配額 | 上限 |
  |------|------------|------|
  | `gemini-3.6-flash` | `GenerateRequestsPerDayPerProjectPerModel-FreeTier`（每模型每日請求數） | 20 次 |
  | `gemini-3.5-flash` | `GenerateContentInputTokensPerModelPerMinute-FreeTier`（每模型每分鐘輸入 tokens） | 25 萬 |

  - 額度用完（429）時，對同一模型重試只是在等待；備援模型的額度是分開計算的，所以 429 改成直接換備援模型
  - 額度的實際計算方式無法從外部確定，觀察到的現象彼此不一致，所以都不當成固定規則：
    - 3.6-flash 回傳「每日」請求數用完後，過幾分鐘又能成功呼叫
    - 3.5-flash 在 2026-09-24 因每分鐘 tokens 上限拒絕了 136 分鐘的影片，但 2026-09-30 又成功處理了同一支影片

## 4. 摘要從「每位使用者」改存到「影片」那一層

**原本的問題**

資料庫有兩層：

- `videos`：共用的影片快取，同一支影片只存一筆
- `user_videos`：每位使用者自己的狀態（已讀、收藏、筆記）

AI 摘要與中文標題原本存在 `user_videos`，也就是每位使用者各存一份。同一支影片如果有 N 位使用者點開，就會呼叫 Gemini N 次，產生 N 份內容相近的摘要：

- 成本變成 N 倍（13.6 分鐘的影片約 7.4 萬 tokens）
- 免費方案的影片額度會被重複消耗
- 每位使用者要各自等待生成

當時只有我自己使用，所以沒有立即影響；但這是產品一旦有多位使用者就會放大的成本結構問題。

**決策（2026-09-30 實作）**

- 摘要、中文標題、處理狀態搬到 `videos`；`user_videos` 只保留已讀、收藏、個人筆記
- 摘要和影片是一對一的關係，所以直接放在 `videos`，不另開 `video_summaries` 表，查詢比較簡單
- 每份筆記記錄生成時使用的模型、章節數與 prompt 版本，之後 prompt 改版時可以找出哪些是舊版筆記
- 第一位使用者觸發生成，之後的使用者直接讀取

**多人同時使用時的兩個問題**

| 問題 | 做法 |
|------|------|
| 兩個人同時按「生成筆記」，會重複呼叫 Gemini | 用一個條件式的資料庫更新「搶」處理權，只有一個請求會成功，其他請求拿到目前狀態 |
| 伺服器在生成途中重啟，影片會永遠卡在「處理中」 | 記錄開始時間，超過 15 分鐘視為中斷，可以重新觸發；舊的那次就算之後才跑完，也不能覆蓋新的結果 |

**資料遷移**

- 既有筆記不會遺失：每支影片保留最新的那份筆記
- 處理中或失敗的狀態不搬移，因為重新觸發即可
- 可以退回舊結構：每位擁有該影片的使用者都會拿回筆記

**驗證**

- 用舊結構塞入測試資料，確認升級、退回、再升級的結果都正確
- 在 Postgres 上以假的 AI 回應測試，不消耗 Gemini 額度：
  - A 生成的筆記 B 可以直接讀取，不會再呼叫 Gemini
  - 3 個請求同時觸發同一支影片，只呼叫 1 次
  - 卡住 15 分鐘以上的工作可以重新觸發，剛開始的不會
  - 收藏仍是個人各自的
- 用真的 Gemini 跑過一次完整流程

**取捨**

- 筆記的章節是用「第一位觸發者」的 YouTube 授權去讀取的；讀不到章節時仍會生成筆記，只是沒有章節定位
- 生成失敗時，所有人看到的都是同一個錯誤狀態，任何人都可以重試

## 5. 影響信任的 Bug 修正

整理作品集時修正的問題。共通點是：功能看似正常，但使用者看到的結果是錯的或難以使用，會直接削弱對產品的信任。

| 問題 | 使用者看到的現象 | 原因 | 修正 |
|------|------------------|------|------|
| 同步永遠顯示 0 部 | 按「同步」後永遠顯示「找到 0 部新影片」，影片列表也不會更新 | API 把同步丟到背景執行，立刻回傳寫死的 `new_videos=0` | 同步在請求內完成並回傳真實數量；頻道並行抓取（上限 5 個）；部分頻道失敗時照實顯示 |
| 摘要沒排版 | AI 筆記顯示成一整塊純文字，沒有標題大小、沒有項目符號 | 使用了 Tailwind 的 `prose` 樣式，但沒安裝 typography 外掛 | 安裝 `@tailwindcss/typography` 並調整深色主題樣式 |
| 通知提示異常 | 提示訊息沒有動畫；多則提示時，前一則的計時會被重置 | 引用了不存在的動畫 class；計時器依賴會變動的值 | 補上動畫；計時器改綁每則提示的 id |
| 手機篩選面板自動關閉 | 在手機上輸入一個字，篩選面板就關掉 | 每次篩選變更都會關閉面板 | 面板保持開啟，直到按「查看結果」、關閉鈕、背景或 Esc |
| 搜尋每打一個字就送出請求 | 輸入時畫面閃爍 | 沒有延遲送出 | 停止輸入 300 毫秒後才搜尋，並在載入時保留上一批結果 |
| 卡片預覽顯示原始 Markdown | 影片卡片出現 `##`、`**` 等符號 | 直接截取摘要原文 | 預覽只取內文、略過段落標題 |
| 返回鍵離開網站 | 從分享連結直接打開影片頁，按「返回」會離開 Brevora | 一律執行瀏覽器上一頁 | 沒有站內上一頁時改回首頁 |
| 時間戳格式不一致 | 有些筆記的時間戳是高亮程式碼樣式，有些是一般文字 | prompt 用反引號示範格式，模型有時照抄 | 移除 prompt 中的反引號；顯示時統一格式 |

## 6. 長影片的時間戳會偏移 → 用創作者章節定位

**問題**

時間戳改成可點擊之後，錯誤的時間戳會把人帶到影片中不相關的段落。筆記的價值在於「可以回原片查證」，這個錯誤會直接破壞信任。

**驗證方法**

很多創作者會在影片說明欄標註章節，這可以當成可靠的基準（用 YouTube Data API 取得，不需要抓網頁）。把筆記的每個時間戳對應到所在的章節，再逐點比對內容是否相符。

**發現（2026-09-30）**

| 影片 | 結果 |
|------|------|
| 13–105 分鐘的 5 支影片 | 每個時間戳都落在內容相符的章節，最多只在章節交界前後差 1 分鐘以內 |
| 136 分鐘（Huberman） | 五個要點只寫到 1:03:35，後半段約 70 分鐘幾乎沒有涵蓋；而且 1:03:35 這個時間戳本身就是錯的，該主題實際在 1:40:07 |

另外請 Gemini 為這支影片列出完整大綱做對照，結果大綱停在 1:36:30（影片長 2:16:48），同一個主題的時間也和筆記不同。可見影片超過兩小時後，Gemini 對時間位置的判斷就不可靠。

**決策**

- 影片有創作者章節時，把章節交給 Gemini 作為定位依據，要求時間戳落在對應章節內
- prompt 要求五個要點涵蓋影片的前、中、後段；延伸重點也要附時間戳，讓每一點都能查證
- 正式產品在處理影片時用 YouTube Data API 抓章節；抓不到時照常生成筆記，不會讓整個處理失敗
- demo 與正式產品使用同一套邏輯，demo 資料會記錄每支影片用了幾個章節（`chapters_used`）

**結果**

Huberman 這支用 33 個章節重新生成後：

- 8 個時間戳中有 7 個落在正確章節，涵蓋範圍延伸到 2:04:22
- 仍有 1 個錯誤：「做不喜歡的事，鍛鍊前中扣帶皮層」標在 1:11:15（實際在講胜肽），該主題應在 0:29:09 或 0:36:08 的章節
- 這次主要模型回傳 503，由備援模型 `gemini-3.5-flash` 生成

**取捨與限制**

- 章節能大幅改善定位，但不保證每一點都正確。筆記的定位是篩選工具，時間戳的作用正是讓讀者自己回原片確認
- 沒有章節的長影片仍然可能偏移
- 其他 5 支影片是在加入章節功能之前生成的（`chapters_used` 為 0）。驗證後時間戳正確，為了節省免費額度沒有重跑
- 每處理一支影片多一次 YouTube Data API 呼叫

## 7. 補上「輸出」：我的筆記

**問題**

README 寫的目標之一是「有輸入也要有輸出」，但產品原本只負責輸入：看完 AI 筆記後，想法沒有地方記。資料庫的 `user_videos.note` 欄位與儲存 API 早就存在，只是前端從來沒有用到。

**決策（2026-09-30 實作）**

- 筆記頁的 AI 筆記下方加上「我的筆記」，看完就能寫，不用切換頁面
- 停止輸入 1 秒後自動儲存，不另外放儲存按鈕；同一時間只送出一個請求，永遠以最新內容為準，避免較舊的內容晚到而蓋掉新的
- 離開頁面前會先存掉還沒送出的內容；儲存失敗時保留輸入的文字，並提供重試
- 純文字、保留換行，上限 5,000 字，前端與後端都會檢查
- 只有空白的筆記視為沒有筆記
- 筆記只存在 `user_videos`，只有自己看得到；「僅顯示有筆記」篩選與搜尋都只會用到自己的筆記
- Demo 模式同樣可以寫，存在訪客自己的瀏覽器

**驗證**

- 後端在一個最後會 rollback 的交易中建立兩個測試帳號，11 項檢查全部通過，資料庫沒有留下測試資料：
  - 5,001 字回傳 422，5,000 字可以儲存
  - 另一個帳號看同一支影片看不到別人的筆記，篩選與搜尋也找不到
  - 只有空白或換行的筆記不算有筆記
- 在瀏覽器實測自動儲存、重新整理後內容仍在、輸入後不到 1 秒就離開頁面、斷線時失敗與重試、卡片標示、篩選、搜尋、清空筆記，完整版與 Demo 模式結果一致

**取捨**

- 不支援 Markdown、匯出與分享，之後有需要再加
- 輸入後不到 1 秒就直接關閉分頁時，程式會請瀏覽器先詢問是否離開；如果選擇離開，最後這段內容不會儲存（這個情境尚未在瀏覽器實測）
- 「只有空白不算有筆記」的判斷，後端用 Postgres 正規表示式（`~ '\S'`）。一開始用 `trim()`，測試時發現它不會去掉換行，才改成這個做法

## 8. 安全性修補

**背景**

整理作品集時列出 5 個安全問題。這個產品目前只有我自己使用，所以沒有實際發生過事件；但這些都是一旦有其他使用者、或部署到公開環境，就會直接造成風險的問題。

**依風險排序與做法**

| 問題 | 風險 | 做法 |
|------|------|------|
| `JWT_SECRET` 預設值是公開在 repo 裡的 `change-me-in-production`；沒設 `ENCRYPTION_KEY` 時，Google token 以明文存進資料庫 | 最高：知道預設值就能偽造任何人的登入 | 移除預設值；後端啟動時檢查，不合格就拒絕啟動，並顯示產生金鑰的指令 |
| OAuth 登入沒有 `state` 參數 | 中：攻擊者可以讓別人在不知情下登入成攻擊者的帳號（login CSRF） | 後端產生隨機 state，放進只有伺服器讀得到的 cookie；Google 回呼時比對，不一致就拒絕 |
| 登入後的 JWT 放在網址參數 `?token=`，有效 7 天 | 中：會留在伺服器存取紀錄與瀏覽器歷史 | 網址只帶一次性交換碼（60 秒內有效、用一次就失效），前端再拿它向後端換 JWT。最初的做法是把 JWT 改放在 `#` 之後，本機實測發現仍會留在瀏覽器歷史，見下方「本機實測後的修正」 |
| AI 生成失敗時，原始錯誤訊息直接顯示在畫面上 | 中：Gemini 的錯誤內容包含專案編號與額度資訊，筆記共用後所有使用者都看得到 | 完整錯誤只寫進伺服器 log；畫面依錯誤類型顯示安全的說明 |
| Google access token 換新後沒寫回資料庫 | 低（安全）、中（效能）：過期後每次呼叫 YouTube 都要多換一次 token | 呼叫前先檢查過期並換新，新 token 加密後寫回；同步多個頻道時只換一次 |

**考慮過但沒採用**

- **JWT 改放在 HttpOnly cookie**：可以防止 XSS 讀到 token，但前後端部署在不同網域時，要另外處理跨網域 cookie 與 CSRF，改動範圍太大。目前 JWT 仍存在 localStorage，這是已知的取捨

**驗證**

- 雲端（Postgres，Google 與 YouTube 以假的回應代替）：
  - 密鑰：沒設定、仍是舊預設值、長度不足、金鑰格式錯誤都會拒絕啟動，設定正確時正常啟動
  - 錯誤訊息：額度用完、服務忙碌、其他錯誤各自顯示對應的說明，專案編號不會出現在畫面上
  - token：過期的 token 只換一次並加密寫回；同步 5 個頻道只換一次；換新失敗的筆記也不會遺失已換好的 token
  - 登入：state 不一致、缺少 state、在別的瀏覽器回呼都會被拒絕，且不會建立帳號；（第一版 `#token` 做法）JWT 只出現在 `#` 之後
  - 前端（第一版 `#token` 做法）：token 讀取後就從網址列消失，按「上一頁」不會回到含 token 的網址；但瀏覽器的全域歷史紀錄仍會留下，見下方「本機實測後的修正」
- 本機（2026-10-06）：用真實的 Google 帳號完成登入、取消登入、同步與 token 換新。過程中發現下面兩個問題

**本機實測後的修正（2026-10-06）**

| 發現 | 原因 | 修正 |
|------|------|------|
| 登入成功卻停在登入頁 | 開發模式的 React `StrictMode` 會讓 effect 執行兩次。第一次讀到 JWT 並清掉網址，第二次讀不到，就把人導回 `/login` | 回呼頁只處理一次（#9） |
| JWT 仍留在瀏覽器歷史 | 在 Chrome 的 `chrome://history` 搜尋，查到一筆 `localhost:5173/callback#token=…`。瀏覽器在頁面導向的那一刻就記錄了完整網址，前端事後清除網址只影響「上一頁」，管不到全域歷史紀錄。這份 7 天有效的 JWT 登出後仍然可用，開了 Chrome 同步還會同步到其他裝置 | 改用一次性交換碼 |

一次性交換碼的做法：

- Google 回呼後，後端產生隨機代碼，只把它的 SHA-256 雜湊存進 `login_codes` 資料表，導向 `/callback#code=…`
- 前端讀到代碼後清掉網址，呼叫 `POST /auth/exchange` 換到 JWT。代碼 60 秒內有效；後端用一次「刪除並回傳」的資料庫操作來確認並作廢代碼，所以同一組代碼只能成功換一次
- 產生新代碼時順便刪掉過期的舊資料，資料表不會一直變大
- 歷史紀錄裡留下的只會是已經失效的代碼。從歷史紀錄重新打開這個網址，會回到登入頁並顯示「登入連結已失效」
- 存在資料表而不是記憶體：開發時後端改程式會自動重啟，正式部署也可能有多個 worker，記憶體裡的代碼都會遺失

驗證：

- Migration：在本機資料庫升級、退回、再升級都正常，既有資料筆數不變
- 後端（建立暫時的測試帳號，測完刪除）：有效代碼換得到 JWT；同一組代碼第二次使用、過期代碼、不存在的代碼都會被拒絕；5 個請求同時使用同一組代碼，只有 1 個成功；資料表裡查不到原始代碼
- 本機 Chrome：正常登入後直接進入影片列表；`chrome://history` 只剩 `/callback#code=…`，找不到 `token=`；從歷史紀錄重新打開會顯示「登入連結已失效」；開發模式下每次登入只呼叫一次 `/auth/exchange`。取消登入、偽造回呼、token 換新重測也都正常
